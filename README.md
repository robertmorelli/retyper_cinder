# Detyper
This is a tool for testing the performance of cinderx at different "proportions of typedness": the fraction of annotation groups with a useful (not Any) type to all annotations groups in the target code. Samples are generated by a 4 part tool which removes useful annotations and then repairs the resulting code.
## Fact Gathering

for all expressions in a program... make vertices and edges
far all expressions in a program you can consider the actual type of any expression and the obligations an expression might have to fulfill. For instance, passing an argument to a parameter. The argument must fulfill the type of the parameter as per the function signature; that would be an example of an obligation. A value reassigned to a declared variable must be compatible with the variables declared type. Therefore the value must meet the obligation to the type in order to be a valid assignment.

This uses a modified cinderx type binder and some post processing to gather facts about the code being processed. This modified type binder collects the following data:
- All type binding results for expressions.
- All type 'contexts' for expressions. The type for which a type binding is compared to in order to determine validity
- Collections of linked annotations like inherited members within a class hierarchy
- Inflow of annotations: assignments to variables, the expression in a return statement, an argument to a parameter
- Outflow of annotations: reads from variables, call sites of functions, uses of parameters. The inverse table is also collected.
- Locations of all uses of constructors

These tables are then "cleaned" to reduce false positives that would lead to unnecessary or incorrect patch insertion

## Typedness Flow Graph
The typedness flow graph is a data structure which approximates the decisions of a type checker in a gradual language by encoding the flow from an annotation to a bound expression type and context. It is used to determine if a given expression still has the same type (or predict the resulting type) after annotations are removed. The graph assumes that the topologies of a fully typed and partially detyped program are related (in regards to the flow of typedness). The graph can predict the type and context of an expression by using the collected facts as a heuristic.

## Annotation Remover
As the title suggests, it removes annotations. It also does a few more important tasks. First, it ensures that representation of containers remains the same even if an annotation is removed. CheckedLists, for instance, can be constructed with a simple list literal. Since the annotation removal changes the meaning of the literal, it is replaced with an explicit constructor.

## Type Mediation
Type mediation is the process of inserting casts ("patches"), boxes and primitive constructors in appropriate locations in order to satisfy the cinderx type checker. The "mediation" reconciles the typed and untyped portions of the program. The mediator uses the Typedness Flow Graph in order to predict locations of type disagreements and the Patch Picker decides what (if any) remedy is needed. After a patch is picked and inserted, a one hop propagation is run on the graph as an approximation for a full fixed point iteration over the graph. The mediator follows a postorder traversal as an approximation for an additional fixed point iteration due to the fact that most flow edges point "up and to the right". Since all patches are inserted as soon as, and only when, a disagreement is discovered, the selection of patches is in some sense "greedy". I suspect that a related graph construction may find a true global minimum of necessary patches by a min cut reduction but that is thus far unproven. The mediator also has a few other jobs which all broadly fall under the category of optimizations. There is code to reduce patch "towers". A tower of patches is any expression with a useful value wrapped in multiple patches. Unary operators are transparent to this optimizer: boxes float outside a unary tower, while primitive constructors sink to its operand, so `-box(value)` normalizes to `box(-value)` and `int64(-value)` normalizes to `-int64(value)`. This deliberately assumes that boxing and primitive construction commute with every unary operator supported by the input program. Additionally some primitive patches located at the "top" of an if/while/index are removed in cases where they are not needed. In appropriate places, clen and len are swapped in order to improve performance of output code or to reduce the need for a patch.
