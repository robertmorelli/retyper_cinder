# Detyper
This is a tool for testing the performance of cinderx at different "proportions of typedness": the fraction of annotation groups with a useful (not Any) type to all annotations groups in the target code. Samples are generated by a 4 part tool which removes useful annotations and then repairs the resulting code.
## Fact Gathering

for all expressions in a program... make vertices and edges
far all expressions in a program you can consider the actual type of any expression and the obligations an expression might have to fulfill. For instance, passing an argument to a parameter. The argument must fulfill the type of the parameter as per the function signature; that would be an example of an obligation. A value reassigned to a declared variable must be compatible with the variables declared type. Therefore the value must meet the obligation to the type in order to be a valid assignment.

This uses a modified cinderx type binder and some post processing to gather facts about the code being processed. This modified type binder collects the following data:
- All type binding results for expressions.
- All type 'constraints' for expressions. The type for which a type binding is compared to in order to determine validity
- Collections of linked annotations like inherited members within a class hierarchy
- Inflow of annotations: assignments to variables, the expression in a return statement, an argument to a parameter
- Outflow of annotations: reads from variables, call sites of functions, uses of parameters. The inverse table is also collected.
- Locations of all uses of constructors

These tables are then cleaned to reduce false positives that would lead to unnecessary or incorrect edit insertion.

## Typedness Flow Graph
The typedness flow graph is a data structure which approximates the decisions of a type checker in a gradual language by encoding the flow from an annotation to a bound expression type and constraint. It is used to determine if a given expression still has the same type (or predict the resulting type) after annotations are removed. The graph assumes that the topologies of a fully typed and partially detyped program are related (in regards to the flow of typedness). The graph can predict the type and constraint of an expression by using the collected facts as a heuristic.

## Annotation Remover
As the title suggests, it removes annotations. It also does a few more important tasks. First, it ensures that representation of containers remains the same even if an annotation is removed. CheckedLists, for instance, can be constructed with a simple list literal. Since the annotation removal changes the meaning of the literal, it is replaced with an explicit constructor.

## Type Mediation

Type mediation inserts casts, boxes, and primitive constructors where typed
and untyped regions meet. The implementation follows four abstraction layers:

1. `mediate_ast.py` walks expression positions.
2. `optimal_mediation.py` compares plausible multi-operand mediations.
3. `select_mediation.py` resolves one mediation request.
4. `edits.py` implements the selected AST edit.

`mediate_expression.py` dispatches an expression to the appropriate mediation
path. `UnopSpine` represents coercions and unary operators surrounding an
expression, allowing edits to move across unary operators without exposing AST
reconstruction to the selection layer.
